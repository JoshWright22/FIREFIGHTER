# Learn agent peaks, buffer the human, admit conservatively

The systems that share machines well split the problem in two, and FIREFIGHTER should too. **Background workloads are predicted from their own history**: Google Autopilot, Kubernetes VPA, Borg, BOINC and the HPC runtime predictors all keep per-job usage history, use a high percentile or the peak for memory, the mean for CPU, add a 10–15% margin, rise fast and fall slowly, and treat a job with no history at its declared limit. **The protected primary (here, the human) is mostly not forecast far ahead.** Instead it is protected by a measured buffer plus fast reaction: PerfIso keeps B idle cores, Heracles disables batch work at 85% load, Senpai and systemd-oomd act on memory pressure, and IOCost and LEDBAT act on latency. Desktop scavengers (HTCondor, BOINC) add presence detection with asymmetric hysteresis. The research adds two longer-horizon tools: hour-of-week profiles (Ren et al., more than 86% accuracy for windows of up to 10 hours) and distribution-free bounds on how long the user stays away (Brevik et al., correct 96% of the time at a 95% target). For FIREFIGHTER this means a per-(agent, project, command) store of run peaks with Autopilot/VPA/BOINC update rules, a human reserve computed as max(peak of the last 120 s × 1.1, the hour-of-week high percentile, a context floor), and admission based on the sum of predicted peaks for fatal resources (RAM, VRAM, disk space) and an N-sigma/percentile test for throttleable ones (CPU, disk I/O, network). No published system learns one human desktop user's demand for each resource. That part of the design is inference built from verified parts. The constants below come from the papers and source files, and the ones I chose are marked as mine.

## Production systems predict the batch job but buffer the primary

All the sources answer two different questions. The first is how much a given background job will use. That is a learning problem, and every scheduler that solves it does so from the job's own past runs. The second is how much the latency-sensitive primary needs right now. Production systems mostly do not answer that with a long-range forecast. They keep a measured headroom and take resources back within milliseconds to seconds. PerfIso on Windows/Bing uses the rule "**if I < B, S is decreased, and if I > B, S is increased**" (I = idle cores, B = buffer cores, S = secondary cores), and found "8 cores are enough" on 48-core servers. It ran on more than 90,000 servers and raised off-peak CPU use from **21% to 66%** without hurting tail latency ([PerfIso §3.1, §4.1](https://ktisis.cut.ac.cy/bitstream/20.500.14279/19430/1/atc18-iorgulescu.pdf)). Heracles polls every 15 s, disables best-effort work above **85% load** or at negative latency slack, re-enables it below **80%**, freezes growth below **10%** slack, removes cores below **5%**, and gives everything to the primary for about 5 minutes after a violation ([Heracles Alg. 1](http://csl.stanford.edu/~christos/publications/2015.heracles.isca.pdf)). SmartHarvest is the one system that predicts the primary, and only 25 ms ahead. Its important rule for FIREFIGHTER concerns data hygiene: it "**discard[s] any data collected during periods of full utilization by the primary**", because a saturated primary's usage understates its demand ([SOL §5.2](https://arxiv.org/pdf/2201.10477)).

Desktop cycle scavengers use the same split with presence added. HTCondor's shipped desktop policy (verbatim in `param_info.in`) starts guest work only after `KeyboardIdle > 15 min` and `NonCondorLoadAvg <= 0.3`. It suspends on a keystroke within 1 minute, or when non-Condor load stays at or above 0.5 for 120 s, and continues only after 5 minutes idle ([HTCondor param_info.in](https://raw.githubusercontent.com/htcondor/htcondor/main/src/condor_utils/param_info.in)). BOINC separates "user present" (`idle_time < idle_time_to_run*60`, default 3 min) from "user consuming CPU": it suspends when `non_boinc_cpu_usage*100 > suspend_cpu_usage` (default 25%) and holds the suspension for at least 20 s. Its RAM budget is 50% of RAM while the user is busy and 90% while idle, and by default it keeps the GPU off while the user is active ([BOINC prefs.cpp](https://raw.githubusercontent.com/BOINC/boinc/master/lib/prefs.cpp); [cs_prefs.cpp](https://raw.githubusercontent.com/BOINC/boinc/master/client/cs_prefs.cpp); [client_state.cpp](https://raw.githubusercontent.com/BOINC/boinc/master/client/client_state.cpp)). The trick both use is the one FIREFIGHTER needs for every resource. **The human's usage is total minus the scheduler's own**: BOINC computes `non_boinc_cpu_usage = max(0, nbrc - prev_nbrc) / (delta_t * ncpus)` from total CPU time minus BOINC-attributed time, sampled every 10 s ([BOINC app.cpp](https://raw.githubusercontent.com/BOINC/boinc/master/client/app.cpp)). HTCondor uses `NonCondorLoadAvg = LoadAvg - CondorLoadAvg`. BITS watches total NIC or gateway bytes and "uses only the idle portion" ([Microsoft BITS](https://learn.microsoft.com/en-us/windows/win32/bits/network-bandwidth)).

The evidence on what users notice sets the size of the buffer. In the controlled study of 33 Windows users, borrowing **0.35 CPU-contention units, 33% of memory, or 1.11 disk writers** discomforted 5% of users overall. In a game (Quake) the thresholds fell to **0.18 CPU contention and 8% of memory**; in Word, CPU tolerance was 3.06 and memory borrowing caused no discomfort at all ([Gupta, Lin, Dinda TR NWU-CS-04-28, Fig. 3.8](https://users.cs.northwestern.edu/~pdinda/Papers/NWU-CS-04-28.pdf)). Running guests at starvable priority cost the owner 0.5% slowdown in simulation ([Linger-Longer SC98](https://www.cs.umd.edu/users/hollings/papers/sc98.pdf)). Ren et al. measured no noticeable (over 5%) host slowdown below 20% host CPU load. Between 20% and 60% the guest had to run at lowest priority, and above 60% it had to stop ([Ren et al. HPDC'06 §3](https://engineering.purdue.edu/dcsl/publications/papers/2006/hpdc06_finegrainedcyclesharing_cameraready.pdf)). The reserve should therefore depend on what is in the foreground, not be one number.

The pattern across these is consistent and fits FIREFIGHTER's data volume. **Memory is sized on the peak because under-provisioning kills.** Autopilot stores only the 5-minute maximum for memory "because… a task is more sensitive to underprovisioning memory (OOM) than CPU (throttled)". Under Autopilot, over 99.5% of job-days were OOM-free, and slack fell from 46–60% under manual limits to 23–31% ([Autopilot §4.2–4.3](https://homepages.dcc.ufmg.br/~cunha/teaching/20221/cloudcomp/readings/10-readings/rzadca20autopilot.pdf)). **Updates are asymmetric**: BOINC jumps up at once and decays at 0.1 per run, Borg "rapidly increase[s]", Autopilot takes the max over the last hour, and ESX takes the max of fast and slow averages ([ESX §5.3](https://www.waldspurger.org/carl/papers/esx-mem-osdi02.pdf)). **Young jobs are trusted least.** Autopilot found slack still above steady state at 14 days and OOM rates at steady state only for jobs 7 or more days old (§4.5). VPA turns this into an explicit widening factor of (1 + 1/confidence).

The notes report that FIREFIGHTER today uses a learned per-command peak × 1.2 that decays 10% per run, a half-life of about 6.6 runs. That already matches Autopilot's S_max-plus-margin for memory. Three pieces are missing: a separate statistic for CPU (the mean, because throttling is cheap), a 4:1 slower decay for memory than for CPU (Autopilot's 48 h versus 12 h), and an explicit kill/OOM bump.

### Agent jobs are spiky, so the key matters more than the model

The only rigorous study of coding-agent workloads measured a **~185 MB framework baseline with tool-call bursts to 2–4 GB**, peak-to-average up to **15.4×**, and bursts lasting 1–2 s that change memory by up to 2.9–3 GB within a second. Average CPU was only 13.2% / 7.6% of one core. **Peak memory showed near-zero correlation with output tokens** (−0.14 / +0.02), varied 197 MB–4 GB across tasks, and varied 1.8× in time across three runs of the same task. Container images averaged 3.5 GB ([AgentCgroup arXiv 2602.09345v2](https://arxiv.org/html/2602.09345v2)). (The notes record OS-level execution as 56–74% of latency in v2 and 55–60% in the v3 abstract; the versions differ.) Two consequences follow. FIREFIGHTER must key history on *what the command is* (test run, `pip/npm install`, Docker build, training, eval, download), not on the agent. And it must read peak counters rather than rely on 2 Hz samples, which can miss 1–2 s bursts. On Linux, cgroup v2 exposes `memory.peak` directly ([cgroup-v2.rst](https://docs.kernel.org/admin-guide/cgroup-v2.html)).

For keys with few runs, 3Sigma's hierarchy is the best published fit. Track several feature levels and use whichever has had the lowest NMAE. The 2^t extension also helps: the estimate is extended only when a job outlives *every* past run ([3Sigma §4.2](https://www.pdl.cmu.edu/PDL-FTP/CloudComputing/eurosys18-final49.pdf)). Heavier cold-start methods suit GPUs better than CPUs. Quasar profiles new work for 5–10 s on two configurations and fills in the rest by collaborative filtering, with errors under 8% on average ([Quasar §3](http://csl.stanford.edu/~christos/publications/2014.quasar.asplos.pdf)). Morpheus fits an LP envelope over aligned past-run skylines, minimizing α·A_o + (1−α)·A_u, with A_u computed by a carried "debt" ([Morpheus §5](https://www.usenix.org/system/files/conference/osdi16/osdi16-jyothi.pdf)). Both need volumes of history a single desktop does not have, so neither should be adopted beyond the "observe the first seconds" idea.

## Admission sums predicted peaks, counting young jobs at their limit

Google's production overcommit predictor answers "will the sum of running work plus this job fit?" for the machine, not for each job. A task is admitted if the predicted machine peak stays under capacity. The predictor is **max(N-sigma, RC-like)**: N-sigma = mean(U) + N·std(U) over the *aggregate* usage, and RC-like = Σ_i perc_k(U_i). Tasks with fewer than `min_num_samples` are added **at their limit**. Production used N = 3, P80, 2 h warm-up and 10 h history, and gained **more than 16%** usable CPU against 10% for the static 0.9 × limit rule at the same risk. The paper also found that "even 1h is a long period for the task usage to reach a steady state": warm-up length barely mattered, while history length did ([Bashir et al. EuroSys'21 §4, §5.3, §6](https://storage.googleapis.com/gweb-research2023-media/pubtools/6074.pdf)). Resource Central's Algorithm 1 adds a second ceiling. A VM is placed only if Σalloc ≤ **125%** and Σpredicted-P95 ≤ **100%** of capacity. In a month-long simulation this gave 0 scheduling failures and 77 readings above 100%, against 6× more for naive oversubscription ([Resource Central §6](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/10/Resource-Central-SOSP17.pdf)). The residual risk it names fits FIREFIGHTER exactly: high percentiles of several jobs "happen[ing] to align in time".

For GPUs the gates are simpler, because VRAM exhaustion is fatal and utilization is not additive. Gandiva runs every new job exclusively first to profile GPU utilization, memory and progress. It packs only "when the combined memory utilization of the packed jobs do not exceed the overall memory of the GPU", and undoes a packing if throughput falls below time-slicing ([Gandiva §5](https://www.usenix.org/system/files/osdi18-xiao.pdf)). Training memory is cyclic, with a max/min ratio up to 77× within a mini-batch cycle (§3), so the peak must be read, not sampled. Static estimators are not safe on their own. PyTorch FakeTensor *under*-estimates by 1.16 GB at P50 and 3.84 GB at P95, and its authors suggest about +4 GB margin. DNNMem's analytical model has a mean relative error of 5.9% on TensorFlow and 14.4% on PyTorch ([arXiv 2602.17817](https://arxiv.org/html/2602.17817v2); [DNNMem](https://www.microsoft.com/en-us/research/uploads/prod/2020/09/dnnmem.pdf)). When GPU jobs queue with unknown durations, Tiresias's least-attained-service priority R_J = W_J·t_J (GPUs × time used so far), with K = 2 queues and a starvation promotion, needs no prediction at all ([Tiresias §3.2](https://www.usenix.org/system/files/nsdi19-gu.pdf)). AntMan shows the alternative to accurate prediction: elastic memory that spills tensors to host RAM so a burst does not OOM. It requires framework changes FIREFIGHTER cannot make ([AntMan](https://www.usenix.org/system/files/osdi20-xiao.pdf)).

## Each resource has a proven reactive guard to back the prediction

**Memory.** Meta's TMO replaced "usage" with "pressure". Senpai reclaims `current_mem × reclaim_ratio × max(0, 1 − PSI_some/PSI_threshold)` every 6 s, with **reclaim_ratio = 0.0005, PSI_threshold = 0.1%**, at most 1% of the workload per period. Expansion is immediate. TMO saved 20–32% of memory fleet-wide ([TMO §3.3](https://www.cs.cmu.edu/~dskarlat/publications/tmo_asplos22.pdf)). The open-source loop tightens `memory.high` by at most 1% and loosens by up to 100% per step. Its defaults are `--interval 6`, `--pressure 10000` µs, `--coeff-probe 10` and `--coeff-backoff 20` ([senpai.py](https://github.com/facebookincubator/senpai/blob/main/senpai.py)). The value Senpai settles on is the job's real working set, a better learning target than RSS, which includes reclaimable cache. For the human, Android lmkd triggers at a **70 ms partial / 700 ms complete stall per 1 s** ([AOSP lmkd](https://source.android.com/docs/core/perf/lmkd)). systemd-oomd kills at PSI full avg10 > **60% for 30 s** (Fedora: 20 s) or swap > 90% ([oomd.conf](https://www.freedesktop.org/software/systemd/man/latest/oomd.conf.html)). Fedora's uresourced gives the active user a fixed `memory.low` of 250 MiB, capped at 10% of RAM ([Fedora change](https://fedoraproject.org/wiki/Changes/Reserve_resources_for_active_user_WS)). That is the static floor a learned reserve would replace. Windows has no PSI. The documented knobs there are memory priority 1–5 ("lower memory priority are trimmed before" higher) and Job Objects ([MEMORY_PRIORITY_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-memory_priority_information)). ESX's active-set estimate (100 random pages per 30 s, max of fast EWMA, slow EWMA and the current period) is the portable pattern ([Waldspurger OSDI'02 §5.3](https://www.waldspurger.org/carl/papers/esx-mem-osdi02.pdf)).

**CPU.** Short-horizon prediction of host load works with tiny linear models. Dinda's AR(16) on 1 Hz load, fitted to 300 samples and refitted when error drifts, was "the best all around model for host load predictions of 1-30 seconds", with confidence intervals about half the width of MEAN's ([Dinda & O'Hallaron HPDC'01](https://users.cs.northwestern.edu/~pdinda/Papers/hpdc01-rta.pdf)). But PerfIso's buffer rule makes that unnecessary for protection. Enforcement on Windows uses Job Object `CpuRate` (1/100 % units, `HARD_CAP` 0x4, `WEIGHT_BASED` 1–9 default 5, `MIN_MAX_RATE`) ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_cpu_rate_control_information)) and EcoQoS ([QoS](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)). On Linux it uses `cpu.idle = 1`, Linger-Longer's "starvable" priority, and `cpu.weight` (default 100; systemd's background.slice uses 30) ([cgroup-v2](https://raw.githubusercontent.com/torvalds/linux/master/Documentation/admin-guide/cgroup-v2.rst); [background.slice](https://raw.githubusercontent.com/systemd/systemd/main/units/user/background.slice)).

**Disk I/O and space.** IOCost charges each I/O `base_cost + size_rate × bytes` from six fio-measured coefficients and adjusts a global vrate between min and max when P-percentile latency exceeds a target. The kernel example is `rpct=95 rlat=75000 wpct=95 wlat=150000 min=50 max=150` ([IOCost ASPLOS'22 §3](https://www.cs.cmu.edu/~dskarlat/publications/iocost_asplos22.pdf); [cgroup-v2 io.cost](https://docs.kernel.org/admin-guide/cgroup-v2.html)). `io.latency` throttles peers once a protected group misses its target; for rotational disks the docs advise setting the target 10–15% above avg_lat. mClock's tags (R = max(R_prev + 1/r, t), L, P likewise) give reservation, limit and weight per tenant ([mClock §3](https://www.usenix.org/legacy/event/osdi10/tech/full_papers/Gulati.pdf)). For space, BOINC's allowance is the only verified algorithm: `limit = own_usage + free − min_free; limit = min(limit, total×max_pct/100, max_gb); max(limit,0)` with defaults 90% and 0.1 GB ([cs_prefs.cpp](https://raw.githubusercontent.com/BOINC/boinc/master/client/cs_prefs.cpp)). Delivery Optimization caps its cache at 20% of free space ([DO reference](https://learn.microsoft.com/en-us/windows/deployment/do/waas-delivery-optimization-reference)). **No primary source on forecasting per-tenant disk-space growth was found.**

**Network.** BwE's demand estimator is history-free and fits per-job throughput: "**Demand = max(max_Δt(usage) × scale, min_demand)**" with Δt = 120 s, scale = 1.1 and min_demand = 10 Mbps. Its authors' reason for estimating rather than asking: "user estimates are wildly inaccurate" ([BwE §6.1](https://conferences.sigcomm.org/sigcomm/2015/pdf/papers/p1.pdf)). Heracles leaves headroom for the primary with `BE_limit = LinkRate − LC_bw − max(0.05·LinkRate, 0.10·LC_bw)`. Background downloads should be scavengers. LEDBAT updates `cwnd += GAIN × (TARGET − queuing_delay)/TARGET × bytes_acked × MSS/cwnd`, with TARGET ≤ 100 ms, GAIN ≤ 1 and BASE_HISTORY 10 one-minute minima ([RFC 6817](https://www.rfc-editor.org/rfc/rfc6817.txt)). On Windows, BITS already "enables LEDBAT on HTTP connections" and uses only idle bandwidth ([BITS](https://learn.microsoft.com/en-us/windows/win32/bits/network-bandwidth)).

**The human's longer horizon.** Three verified tools predict minutes to hours ahead. First, absence has a decreasing hazard: Weibull shapes of 0.49–0.61 on real pools mean the longer a machine has been idle, the longer it tends to stay idle ([Nurmi et al. Euro-Par'05](https://sites.cs.ucsb.edu/~rich/publications/europar05.pdf)). Mutka fitted available intervals with `F(t) = 0.33(1−e^{−t/3}) + 0.44(1−e^{−t/25}) + 0.24(1−e^{−t/300})` (minutes) ([Mutka dissertation](https://chtc.cs.wisc.edu/doc/mutka-dissertation.pdf)). Second, Brevik's binomial method turns a handful of past idle durations into a calibrated lower bound. Sort the samples and pick the largest k with `Σ_{j=0..k} C(n,j)(1−q)^{n−j} q^j ≤ 1 − C`; then x_(k) is a level-C lower bound on the q-quantile. It was correct for 96% of traces at the 0.05-quantile / 95% target, against about 57% for fitted Weibull ([UCSB TR 2003-37 §2.4, Eq. 5](https://www.cs.ucsb.edu/sites/default/files/documents/2003-37.pdf)). Third, Ren's semi-Markov model, fitted on "the same time window on the most recent N weekdays", predicted 10-hour availability windows with **over 86.5% accuracy** and beat AR/ARMA/LAST at long horizons, while linear models won at short ones ([Ren et al. HPDC'06 Eq. 2](https://engineering.purdue.edu/dcsl/publications/papers/2006/hpdc06_finegrainedcyclesharing_cameraready.pdf)). The Network Weather Service (NWS) idea of running several predictors and using the one with the lowest cumulative error is attractive. Its rule is confirmed only in secondary sources, and a later paper reports 20% better accuracy than NWS's selection ([LARPredictor IPDPS'07](https://www.cecs.uci.edu/~papers/ipdps07/pdfs/IPDPS-1569011105-paper-1.pdf)).

## Recommended design for FIREFIGHTER, resource by resource

### Shared machinery

**Attribution.** At 2 Hz FIREFIGHTER should compute, per resource r, `agent_r = Σ over running job trees` and `human_r = max(0, total_r − agent_r − baseline_r)`, as BOINC, HTCondor and BITS do. Here baseline_r is the idle-OS floor, learned as the P10 of total usage over away periods. Every job runs in a Windows Job Object or a Linux cgroup so its peaks are accounted for even between samples.

**Agent history.** Keep a ring of the last **20 run records** per key at four levels: (agent, project, command signature) → (project, job kind) → (job kind) → global. Each record holds per-resource peak, mean, P95, duration, whether the run was killed/OOM/throttled, and the time of day. The prediction comes from the most specific level with **at least 2 runs**. Once two or more levels have 3 or more runs, switch to the level with the lowest NMAE of past point predictions (3Sigma §4.1).

**Agent predictor.** Weight each run by `w = 2^(−age_in_runs / h)`. "Fatal" resources (RAM, VRAM, disk-space growth) use `pred = 1.15 × max_w(peak)` with **h = 8 runs**. Throttleable resources use `pred = 1.10 × weighted mean` with **h = 2 runs**, which keeps Autopilot's 4:1 memory-to-CPU half-life ratio (my run-count translation). Rise fast, fall slowly: the new prediction is `max(new, 0.9 × previous)` (BOINC's α_down = 0.1). A kill, OOM or VRAM-OOM inserts a synthetic sample `max(1.2 × base, base + 100 MiB)` (VPA RecordOOM). Runtime is the mean of the last 2 runs (Tsafrir). Past the longest observed run, extend by 2^t × the 2 s tick (3Sigma).

**Cold start (all resources).** With 0 runs, use the declared value if the agent gave one. Otherwise use the P90 of the job kind's predictions across all keys. Otherwise use a fixed prior: 4 GB RAM (AgentCgroup's 2–4 GB peaks), the full declared GPU or 8 GB VRAM, 2 cores, and 5 GB disk (3.5 GB average image plus margin; my choice). With 1–4 runs, multiply the fatal-resource prediction by `(1 + 1/n)`, which is VPA's confidence widening counted in runs. Until a job has run **60 s**, admission counts it at its predicted peak or declared limit, whichever is larger (Borg's 300 s and Take-it-to-the-limit's warm-up rule, shortened for desktop jobs).

**Human profile.** Use 168 hour-of-week slots, each holding a decayed histogram of human_r *while present*, with a **14-day half-life**, plus p(present) per slot (Mutka's hourly Bernoulli). CPU uses the load-weighted P95 (Autopilot Eq. 3). RAM and VRAM use the P98 of 5-minute peaks (the Autopilot memory signal). Disk and network use the P95 of 120-s peaks. **Discard samples where the resource was ≥ 95% used or FIREFIGHTER was throttling agents for the human** (SmartHarvest's censoring rule). Store a second profile keyed by foreground-app class (game/fullscreen-3D, IDE/office, browser, media). The 14-day half-life and the class keys are my choices.

**Human reserve.** `Reserve_r(t, D) = max(Short_r, Profile_r, ContextFloor_r)`. Here `Short_r = 1.1 × max(human_r over the last 120 s)` (BwE). `Profile_r` is the max over the slots in [t, t+D] of the slot statistic for which p(present) ≥ 0.2, where D is the job's predicted duration. `ContextFloor_r` comes from the foreground class (table below). This reserve is the answer to "how much will the user use": a near-term peak plus the habitual peak for the hours the job will span.

**Presence and timing.** Keep asymmetric hysteresis: react to input within one sample, but trust absence only after minutes. HTCondor uses 15 min to start and 5 min to continue; FIREFIGHTER's current 180 s / 10 s sits within the literature's range. For a job that cannot be paused cheaply (GPU training without checkpoints, Docker builds), start it only when Brevik's 95%-confidence lower bound on *remaining* absence is at least its predicted duration. Compute the bound from past away episodes that already lasted longer than the current one, to use the decreasing hazard. With fewer than 10 such episodes, fall back to p(present) < 0.2 for every slot in [t, t+D].

The context floor comes from Gupta et al.'s 5%-discomfort points, translated to this machine. When a game or fullscreen 3D app is in front, agents get at most 0.18 cores of extra contention and their RAM is capped at 8% of RAM above what is already admitted. GPU jobs pause. For browser work the IE numbers apply: 0.6 contention and about 30% of RAM. For IDE/office work CPU contention may reach about 1 core per 16 and RAM 33%. Above that, the PerfIso buffer and the PSI/latency guards take over. The translation from 2004 single-core figures to a 16-core PC is my extrapolation, so it should be checked by FIREFIGHTER's own "the human noticed" signal: input lag, PSI spikes, or the human pausing jobs by hand. Each such event should raise that class's floor by 20% (the VPA bump factor reused).

### How prediction and reserve combine at admission

```
admit(job j, now t):
  D      = predicted_duration(j)                      # Tsafrir mean-of-last-2 / prior
  for r in {CPU, RAM, VRAM, DISK_SPACE, DISK_IO, NET}:
      need_j = predict(j, r)                          # key hierarchy, asymmetric, (1+1/n) widening
      load   = Σ_{i running} (age_i < 60s ? max(pred_i, decl_i) : pred_i)   # fatal r
               or max(mean_agg + 3·std_agg, Σ P80_i)                         # throttleable r
      cap    = Capacity_r − Reserve_r(t, D) − OSfloor_r
      if load + need_j > cap: return WAIT(reason=r)
  if not pausable(j) and LB95(remaining_absence) < D and human_present_likely(t, D):
      return WAIT(reason="human returns before finish")
  return RUN(limits = enforce(pred_j × margins), priority = Eco/idle)
```

## Conclusion

The owner asked FIREFIGHTER to "understand how much usage each agent and user will use". The literature says to treat those as two different estimators with two different safety philosophies. Agents get a learning predictor whose errors are made cheap: peaks for anything fatal, fast-up/slow-down updates, kill bumps, and "count it at its limit until proven". The human gets a predictor whose errors are made *rare*. It is a reserve that is always at least the last two minutes' peak, raised by habit for the hours ahead and by what is in the foreground, and backed by a reactive guard (idle-core buffer, PSI, latency) that never waits for the model. The model only lets agents use more of the machine; it never decides whether the human gets less.

Two findings change the priorities for the next version. First, AgentCgroup's 1–2 s, 15× memory bursts mean the biggest accuracy gain will come from reading per-job peak counters and keying history by command kind, not from a cleverer forecaster. Second, Google found that history length matters and warm-up length does not, and the human profile has no published precedent. So the most valuable thing FIREFIGHTER can start doing now is logging: per-run records for every job, and per-slot, per-foreground-class censored samples of the human. Every predictor above becomes reliable only after a few weeks of that data, and until then the cold-start rules keep the human safe.
