# Put the human above the market, then price every bid

Written 2026-11-03 for firefighter.py as of commit 9ccbed0. Builds on `the earlier Windows-mechanics notes` (2026-10-29), which covered the Windows mechanics: commit caps, memory and I/O priority, PDH GPU counters, sysmem fallback and the suspend-cascade incident. Those are referenced here, not repeated. Labels: **[S]** means the claim is backed by the linked source; **[I]** means it is my inference or a design choice and should be tested before it is trusted.

**Bottom line.** The best design for FIREFIGHTER is a three-layer stack that research and production systems keep arriving at. At the top sits the human, outside any market, protected by a *feedback-controlled* reserve that grows within one poll when you touch the machine and shrinks over tens of seconds when you leave. Microsoft's PerfIso ran this design on Windows Job Objects across more than 90,000 Bing servers and raised CPU use from 21% to 66% without hurting tail latency ([USENIX ATC '18](https://www.usenix.org/conference/atc18/presentation/iorgulescu)). In the middle, agents compete only for what is left, ordered by least attained service per project (Tiresias, Autellix), with bids turned into *paid* urgency drawn from a finite budget. That matters because FIREFIGHTER's current rule, `effective = bid + minutes waited / 10` with nobody paying, makes "always bid 10" a dominant strategy. At the bottom, over-budget work and Salad run as spot capacity and are preempted first. No existing open-source tool does this on Windows. The pieces exist, though, scattered across tiny 2026 agent GPU brokers (AgentLoom, Anvil, gpuq, gpubroker), Windows governors (procgov, Process Lasso), volunteer-computing clients (BOINC), and a decade of papers on DRF, Karma, Themis and PerfIso. The cheapest high-value changes are a user-state reserve controller, priced bids with least-attained-service ordering, VRAM admission learned from each job's past peaks, and a cooperative pause/checkpoint protocol for jobs.

## Five tiny 2026 agent brokers already solved FIREFIGHTER's protocol, but none runs on Windows

The closest prior art is a cluster of 2026 single-developer projects built for exactly FIREFIGHTER's situation: many coding agents sharing one GPU box. **AgentLoom** is "a GPU lease broker for Claude Code sessions". Its daemon owns the truth about devices and leases, and it exposes five MCP tools: `gpu_survey`, `gpu_request`, `gpu_release`, `gpu_extend` and `gpu_report`. A queued session runs `agentloom wait` in the background, ends its turn, and is re-invoked when its lease lands. AgentLoom deliberately does not preempt: "priority reorders the queue; waiting tickets age upward so nothing starves". It "refuses to schedule" on a card running a process it did not start ([GitHub](https://github.com/LH-and-FPGA/AgentLoom)) [S]. **Anvil** (macOS only) runs one job at a time. Agents "submit, keep working, and wake on completion", and each finished job returns a receipt with the outcome, a log tail and the result files; a receipt lost to a killed client comes back on the next wait. Fairness is either `"time"` (equal GPU time per agent) or `"turns"` (round robin). Only listed `operators` (by default the human and the panel) may control other actors' jobs, and GPU work started outside Anvil is shown but never killed ([GitHub](https://github.com/terwgr/anvil)) [S]. **gpuq** learns each job's VRAM from its OOMs, rotates launch turns across projects, and ships an agent skill ([GitHub](https://github.com/lzy248/gpuq)) [S]. **gpubroker** makes each reservation declare `vram_gb`, a priority class and an eviction policy (`never`, `graceful` or `force`). It refuses a reservation when either committed or NVML-observed free VRAM falls below the request plus a margin, and calls this advisory "because consumer GPUs don't offer hard VRAM isolation" ([GitHub](https://github.com/wudaming00/gpubroker)) [S]. **agent-gpu-broker** adds `shared` versus `exclusive` capacity and streams queue position plus an advisory ETA back to the agent ([GitHub](https://github.com/qhy991/agent-gpu-broker)) [S]. All five have 0 to 2 stars and are Linux or macOS only, so their robustness is unproven. What they offer is the agent-facing protocol, which FIREFIGHTER mostly lacks: FIREFIGHTER agents read STATUS.md and block inside `firefighter run` (inference from the code).

On the enforcement side, the Windows-native reference is **lowleveldesign/process-governor** (procgov, 828 stars, active). It applies memory caps, affinity, CPU rate, priority class and efficiency mode through Job Objects, and it can update limits on processes that are already running ([GitHub](https://github.com/lowleveldesign/process-governor)) [S]. It is the code to read before adding Job Object CPU-rate or memory limits. **Process Lasso's ProBalance** supplies the interactive-first policy. It temporarily drops a process that crosses a CPU threshold to Below Normal, never touches "foreground processes and processes that are not causing trouble", and restores the original priority "as soon as the condition passes" ([Bitsum docs](https://bitsum.com/apps/process-lasso/docs/algorithms/probalance/)) [S]. **BOINC** is the most battle-tested "use the PC when the human doesn't" client, and its defaults are concrete. The user counts as active after less than 3 minutes of input idle time. GPU work is suspended while the user is active (`run_gpu_if_user_active = false`) while CPU work continues. Jobs may use 50% of RAM while the user is busy and 90% when idle. Named "exclusive apps" suspend all GPU work until 15 s after they close. CPU-usage suspensions hold for at least 20 s ([prefs.cpp](https://github.com/BOINC/boinc/blob/master/lib/prefs.cpp), [cs_prefs.cpp](https://github.com/BOINC/boinc/blob/master/client/cs_prefs.cpp), [app.cpp](https://github.com/BOINC/boinc/blob/master/client/app.cpp)) [S]. **earlyoom** acts only when both available RAM and swap fall below 10%. It sends SIGTERM at the threshold and SIGKILL at half of it, polls up to 10 times a second, and takes `--prefer`/`--avoid` victim regexes ([GitHub](https://github.com/rfjakob/earlyoom)) [S]. **Pueue**, the one mature queue that fully supports Windows, has no GPU awareness, but its pausable groups ("when you need some processing power right NOW!") are a clean UX model ([GitHub](https://github.com/Nukesor/pueue)) [S]. **Ollama's** scheduler queues models that don't fit and unloads idle ones to make room, and it keeps models resident for 5 minutes by default ([FAQ](https://raw.githubusercontent.com/ollama/ollama/main/docs/faq.mdx)) [S]. Any local model server is therefore a VRAM tenant FIREFIGHTER must count.

The academic side confirms these agent projects are aimed at the right bottleneck. **AgentCgroup** profiled 144 SWE-rebench tasks. It found that memory, not CPU, limits how many sandboxed coding agents can run at once, and that OS-side tool work is a large share of task latency. An eBPF controller aligned with tool-call boundaries cut high-priority P95 latency by 29% under memory contention, though only in trace replay ([arXiv 2602.09345](https://www.arxiv.org/abs/2602.09345)) [S]. **AIOS** shows that simple coordination captures most of the gain. In its ablation, total execution time fell from 152.1 minutes with no scheduler to 74.2 with FIFO and 77.3 with round robin ([arXiv 2403.16971](https://arxiv.org/html/2403.16971v3); code [agiresearch/AIOS](https://github.com/agiresearch/AIOS)) [S]. Heavyweight GPU-sharing machinery barely transfers to this machine. NVIDIA MPS is "only supported on the Linux and QNX operating systems" ([NVIDIA](https://docs.nvidia.com/deploy/mps/when-to-use-mps.html)), HAMi-core's VRAM caps depend on Linux `LD_PRELOAD` ([GitHub](https://github.com/Project-HAMi/HAMi-core)), cuda-checkpoint is Linux-only ([GitHub](https://github.com/NVIDIA/cuda-checkpoint)), and KAI, Volcano and Kueue need Kubernetes [S]. Their *policies* do transfer: KAI's minimum guaranteed runtime before any preemption, and its DRF with reclaim across queues ([GitHub](https://github.com/NVIDIA/KAI-Scheduler)) [S].

## With one GPU, "optimal allocation" collapses into admission control plus ordering

Cluster-scheduling papers optimize placement, gang scheduling and heterogeneity, none of which exist on a single RTX 5070 Ti. What survives is two decisions: *may this job start now without hurting the user or the running job* (admission and packing), and *who goes next* (ordering and fairness). Each resource gets its own best-fit algorithm.

**CPU: a dynamic idle-core buffer beats priority and rate caps.** PerfIso's "CPU blind isolation" keeps B idle cores at all times. It polls the idle-core bitmask in a tight loop, shrinks the batch job's core set at once when idle cores fall below B, and grows it when idle cores exceed B. Static alternatives on Windows Job Objects failed. A fixed core subset left the batch job only 17% of CPU at peak. Capping CPU cycles even at 5% "still produces degradation", because the primary's short-lived threads queued behind the batch work. With 8 buffer logical cores out of 48, P99 stayed within 1 ms of running alone, and 4 was not enough ([PerfIso PDF](https://www.usenix.org/system/files/conference/atc18/atc18-iorgulescu.pdf)) [S]. That directly challenges both FIREFIGHTER's static "2 physical cores" and the October suggestion to lean on Job Object CPU-rate caps. The main knob should be the job's CPU set or affinity, resized by a controller, with idle priority as a second safeguard [I]. Heracles (90% utilization at Google with no latency violations; [Google Research](https://research.google/pubs/heracles-improving-resource-efficiency-at-scale/)) and PARTIES (up to 61% more throughput than Heracles across several latency-critical services; [PDF](https://www.csl.cornell.edu/~delimitrou/papers/2019.asplos.parties.pdf)) generalize the same loop to more resources: grow slowly, shrink fast [S].

**RAM: admit, cap, then kill, because suspension frees nothing.** PerfIso guarantees the primary its memory "by limiting the memory footprint of the secondary. When memory runs very low, secondary processes are killed" ([PDF](https://www.usenix.org/system/files/conference/atc18/atc18-iorgulescu.pdf)) [S]. Android's lmkd adds the ordering and the trigger. It acts on pressure-stall time (critical at 700 ms of complete stall by default), not on free percentage, and it kills by importance bucket (foreground 0, cached 900 and up), heaviest first within a bucket ([Android Developers](https://developer.android.com/topic/performance/memory/guide/kswapd-lmkd-interaction)) [S]. FIREFIGHTER already learned the suspension lesson the hard way (the earlier Windows-mechanics notes §0, finding 1). The upgrade is to order victims by band and then by size, the way lmkd does, and to trigger on a paging-stall proxy [I].

**VRAM: learned peaks with a margin, never live free memory.** Static VRAM estimators are less accurate than they look. In a 2026 comparison over 2,030 TIMM training configurations, PyTorch FakeTensor had a P50 absolute error of 1.16 GB and a P99 of 6.82 GB, and it consistently *underestimated*. GPUMemNet "almost never underestimates" ([arXiv 2602.17817](https://arxiv.org/html/2602.17817v2)) [S]. HF accelerate's `estimate-memory` is accurate to a few percent for *loading* a model, and its docs say to add up to 20% for inference ([docs](https://huggingface.co/docs/accelerate/usage_guides/model_size_estimator)) [S]. On a 16 GB card where the user's VRAM is the thing being protected, the safe estimator is each command's measured historical peak (PDH `GPU Process Memory\Dedicated Usage`, or NVML through [nvitop](https://github.com/XuehaiPan/nvitop)) times about 1.2. The accelerate formula serves as a first-run prior, and an overestimate beats an underestimate [I]. The research on VRAM oversubscription supports a hard limit. Unified-memory oversubscription slowdowns come mostly from page thrashing ([arXiv 2204.02974](https://arxiv.org/pdf/2204.02974)) and were severe on real V100s ([arXiv 1903.02596](https://arxiv.org/pdf/1903.02596)) [S]. WDDM's own docs say over-budget processes "will likely experience stuttering, as they are intermittently frozen and paged-out" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo)) [S].

**GPU compute: pack by complementarity, not by co-locating two GPU jobs.** Tetris scores candidate tasks by the dot product of their demand vector with the free-resource vector and adds a shortest-remaining-time term, for about 30% better job completion time ([PDF](https://xia.cs.cmu.edu/resources/Documents/grandl_sigcomm14.pdf)) [S]. Muri gains up to 3.6x by interleaving jobs that stress *different* resources ([Paper Digest](https://www.paperdigest.org/certificate/c369a1d824ebc4f2)) [S]. Synergy shows GPU jobs need only the CPU they are sensitive to, improving JCT by up to 3.4x ([USENIX](https://www.usenix.org/conference/osdi22/presentation/mohan)) [S]. On this PC the payoff is pairing the GPU holder with CPU-bound builds and scoring rather than with a second GPU job. The 9800X3D has 16 threads, and the earlier Windows-mechanics notes measured how a second GPU job distorts timing [I]. Fine-grained GPU sharing (Salus, AntMan, Orion, TGS) needs framework or driver interception on Linux ([Orion](https://github.com/eth-easl/orion), [Salus](https://github.com/SymbioticLab/Salus), [TGS](https://www.usenix.org/conference/nsdi23/presentation/wu)) [S]. It is a reference, not a tool. One note on the code: `gpu_turn` already admits additional holders while utilization is under 80% (`FILL_BELOW`) and VRAM use is under 70%. So FIREFIGHTER is not strictly one-GPU-job-at-a-time today, and the VRAM-history check matters more than it seems.

**Ordering when runtimes are unknown: least attained service, corrected estimates.** Tiresias's discretized 2D-LAS and 2D-Gittins need no job-length information, or only a history distribution, and come "comparable to … solutions assuming perfect knowledge", up to 5.5x better average JCT than a YARN baseline ([USENIX](https://www.usenix.org/conference/nsdi19/presentation/gu)) [S]. Autellix applies the same least-attained-service idea to agent programs and reports 4 to 15x higher program throughput than vLLM at the same latency ([arXiv 2502.13965](https://www.arxiv.org/abs/2502.13965)) [S]. For runtime claims, the HPC lesson from Tsafrir, Etsion and Feitelson applies directly. User estimates are consistently inaccurate. The fix is to separate the kill limit (the user's estimate) from the system's prediction (here, the average of the same user's last two jobs) and to correct predictions adaptively when they prove wrong ([TPDS PDF](https://www.cse.huji.ac.il/~feit/papers/Pred07TPDS.pdf)) [S]. FIREFIGHTER records `--minutes` but never uses it for ordering, so it can adopt this cleanly: `--minutes` becomes the lease, and history-corrected predictions become the sort key [I].

**Fairness across projects: weighted DRF, integrated over time.** DRF equalizes each tenant's dominant share. Its authors found it to be the only policy they examined that is sharing-incentive, strategy-proof, envy-free and Pareto-efficient at once, and CEEI loses strategy-proofness ([PDF](https://people.eecs.berkeley.edu/~alig/papers/drf.pdf)) [S]. Kueue's production formula ranks queues by "dominant resource usage above nominal quota / weight", serving the lowest share first and preempting the highest ([docs](https://kueue.sigs.k8s.io/docs/concepts/fair_sharing/)) [S]. With one GPU slot, fairness has to be judged over time: charge each project its dominant share of GPU-time, VRAM-GB-hours and RAM-GB-hours, decayed, and serve the lowest per weight [I].

## Free bids make "always 10" the winning move, so bids must cost budget

FIREFIGHTER's market today works like this: the highest `bid + minutes waited / 10` wins, nobody pays, over-budget projects bid 0, and each project gets one ticket. That is a first-price auction with a price of zero, so bidding 10 is weakly dominant for every agent that wants its job done, and the agents' instructions push them to finish tasks [I]. The literature is consistent on the cure. Tycoon's motivation was that plain proportional share gives users "no incentive to honestly report the value of their tasks". Its fix charges credits as the resource is *used*, not when the bid is placed, and gives each user a share equal to bid divided by the sum of bids ([arXiv cs/0404013](https://arxiv.org/pdf/cs.DC/0404013), [cs/0412038](https://arxiv.org/pdf/cs/0412038)) [S]. Lottery scheduling's currencies "flexibly name, share, and protect resource rights". Ticket inflation is safe only among mutually trusting clients, because it dilutes everyone else ([OSDI '94](https://usenix.org/conference/osdi-94/lottery-scheduling-flexible-proportional-share-resource-management)) [S]. That is the formal basis for tying tickets to the *project*, so spawning more jobs never buys more share. Stride scheduling is the deterministic form and is "more predictable and repeatable since it avoids randomness" ([MIT TR-667](https://publications.csail.mit.edu/lcs/pubs/pdf/MIT-LCS-TR-667.pdf); [USF notes](https://cs326-s25.cs.usfca.edu/assignments/project03)) [S]. With a handful of GPU turns per day, a lottery's variance would let one agent lose many draws in a row, so stride (or the equivalent least-attained-service-per-weight rule) is the right form [I]. Teaching implementations exist if needed ([xv6 lottery](https://github.com/avaiyang/xv6-lottery-scheduling), [jv6 stride](https://github.com/jshuhnow/jv6)) [S].

Daily allowances need smoothing, not a cliff. **Karma** (OSDI '23) shows that max-min fairness loses its properties when demand changes over time. Its remedy: users who leave their share unused earn credits, borrowers spend them, and allocation is prioritized by credits. Karma guarantees Pareto efficiency, *online strategy-proofness* and optimal fairness without knowing future demand ([USENIX](https://usenix.org/conference/osdi23/presentation/vuppalapati), [arXiv 2305.17222](https://ar5iv.labs.arxiv.org/html/2305.17222), code [karma](https://github.com/resource-disaggregation/karma)) [S]. FIREFIGHTER's "bids count as 0 past the allowance" is a crude version. A token bucket per project, refilled at allowance/24 h and capped at about 2 days, makes a quiet project bank priority and keeps a hoarder from locking the GPU for hours [I]. **Themis** adds leases and finish-time fairness ρ = T_shared / T_independent, and it auctions only when leases expire, using a partial-allocation auction that "incentivizes truth telling" ([USENIX NSDI '20](https://www.usenix.org/conference/nsdi20/presentation/mahajan)) [S]. Leases are what make runtime claims checkable. **Borg** puts the whole market inside non-overlapping priority bands, where higher bands preempt lower ones and Google oversells quota at low priority ([PDF](https://research.google.com/pubs/archive/43438.pdf)) [S]. That is the outer shell FIREFIGHTER needs, with the human as a band no bid can reach. ESX's **idle memory tax** charges idle pages more than active ones so they are reclaimed first ([OSDI '02](https://static.usenix.org/event/osdi02/tech/waldspurger.html)) [S]. It maps onto agents that park models in VRAM while computing nothing [I].

Evidence on how LLMs bid points toward simple, opaque mechanisms. GPT-4o bidders in InfoBid bid their estimated valuations with full information, but revealing relative positions "disrupts truthful bidding" ([arXiv 2503.22726](https://arxiv.org/html/2503.22726v1)) [S]. LLM bidders play closer to theory in *obviously* strategy-proof formats and reproduce eBay-style late sniping in sealed bids ([arXiv 2507.09083](https://arxiv.org/abs/2507.09083v1)) [S]. In resource-competition games, some models hoard while others hold back ([arXiv 2505.17937](https://arxiv.org/abs/2505.17937v2)) [S]. The Mirage testbed, which ran a non-strategy-proof combinatorial auction, saw users settle into four main strategic behaviors over four months ([Harvard EconCS](https://econcs.seas.harvard.edu/resource/p2pecon05pdf)) [S]. Three conclusions follow [I]. First, the price schedule should be stated plainly in CLAUDE.md, so honest urgency is the obvious best reply. Second, STATUS.md should show each agent its own expected wait and price, not rivals' bid values. Third, a full VCG or combinatorial auction is the wrong tool: for one indivisible slot VCG is just a second-price auction, and for bundles it invites shill bidding by cheaply spawned jobs. No paper yet studies LLM coding agents competing for a local GPU under a scheduler, so the anti-gaming rules below are inference built on these neighboring results.

## The human's reserve must track demand: fast attack, slow decay, measured signals

Every system with a privileged tenant puts it above the market rather than in it: Borg's bands, Linux RT over EEVDF ([Linux Magazine](https://www.linux-magazine.com/Issues/2025/301/EEVDF)), Kueue's reclaim of nominal quota ([docs](https://kueue.sigs.k8s.io/docs/concepts/preemption/)) [S]. What FIREFIGHTER lacks is a reserve that *measures* what the user needs. Its present reserve is static: 2 of 8 physical cores and 5% of RAM (1.6 GB), plus a 60-second input check used only by the disabled duty cycle and a 30-minute away timer for Salad. PerfIso sized its buffer from a profile of how many threads the primary could make runnable at once ([PDF](https://www.usenix.org/system/files/conference/atc18/atc18-iorgulescu.pdf)) [S]. Harvest VMs grow and shrink with a server's unallocated capacity and are evicted only when the provider needs back their minimum, with availability predictions under 2% error short-term ([USENIX OSDI '20](https://www.usenix.org/conference/osdi20/presentation/ambati)) [S]. Fedora's uresourced gives only the *active* graphical user a 250 MiB memory protection, capped at 10% of RAM and zero when no seat is active ([Fedora Change](https://fedoraproject.org/wiki/Changes/Reserve_resources_for_active_user_WS)) [S]. None of these systems sizes a human desktop reserve for GPU and VRAM. That mapping is inference [I].

The signals are available without admin rights. `GetLastInputInfo` gives input idle time per session; its tick can go backwards, which BOINC clamps in [idlemon_win.cpp](https://github.com/BOINC/boinc/blob/master/lib/idlemon_win.cpp) ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getlastinputinfo)) [S]. Windows' own QoS classifier ranks a foreground focused window High, a visible unfocused one Medium, minimized or occluded ones Low, and any process playing audio High ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)) [S]. Those are the same demand signals FIREFIGHTER should copy. Per-PID `GPU Engine` utilization and `GPU Process Memory` are present on this machine (the earlier Windows-mechanics notes §0, finding 8). PresentMon exposes frame time, `InputLatency` and `DisplayLatency` through ETW for a true user-experience metric, though it needs the user in "Performance Log Users" ([GitHub](https://github.com/GameTechDev/PresentMon)) [S]. Input recency only shows that the user is *present*. Foreground CPU, foreground 3D-engine use, VRAM and frame time show what they *need* [I].

On the GPU, Windows already gives part of the protection. FIREFIGHTER sets `D3DKMTSetProcessSchedulingPriorityClass(IDLE)` on every job ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmthk/nf-d3dkmthk-d3dkmtsetprocessschedulingpriorityclass)) [S]. WDDM must request preemption before a TDR, yet long non-preemptible packets still delay DWM and cause "glitches during window transitions and animations" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/gpu-preemption)) [S]. NVIDIA forum guidance is that kernels of "a few millisecond" duration barely affect GUI responsiveness ([NVIDIA forum](https://forums.developer.nvidia.com/t/display-driver-stopped-responding-and-has-recovered-wddm-timeout-detection-and-recovery/15056)) [S]. PilotFish is the strongest academic model. It harvests up to 85.1% of idle GPU time beside a 60 FPS game with no interference, by running training kernels only in gaps they will finish within and preempting any that overrun ([USENIX ATC '22](https://www.usenix.org/conference/atc22/presentation/zhang-wei)) [S]. FIREFIGHTER can't hook graphics libraries, but the protocol shape carries over: jobs yield at step boundaries when told, keep kernels short while the user is active, and empty cached VRAM on request [I]. Volunteer clients show how not to do it. Folding@home's GPU slot makes the system sluggish, and its "on idle" mode has had bugs where the slot never resumed or ran mid-game ([F@H forum](https://forum.foldingathome.org/viewtopic.php?p=335487), [F@H forum](https://forum.foldingathome.org/viewtopic.php?p=336653)) [S]. Two independent signals and a dwell timer guard against both failures [I].

## Recommended design for FIREFIGHTER

Everything in this section is design, labeled **[I]** unless it repeats a sourced number marked **[S]**. Constants are starting points to tune from FIREFIGHTER's own log, not measurements.

### Bands

| Band | Who | Gets | Preempted by | Basis |
|---|---|---|---|---|
| 0 Human | Every process not in a FIREFIGHTER job | Everything up to the reserve R(t); not in any market | Nothing | Borg bands, RT over EEVDF [S]; R(t) sizing [I] |

### Reserve sizing R(t)

User state is computed every 250 ms. **Away** means no input for 3 minutes or more (BOINC's default [S]) and no audio, fullscreen or foreign GPU load. **Present** means input within 3 minutes. **Active** means input within 10 s. **Game/Media** means a fullscreen or borderless foreground window, foreign 3D-engine use above 20% for more than 1 s, a process playing audio, OBS running, or a configured exclusive app (BOINC's `exclusive_gpu_apps` pattern [S]). Every reserve grows in the poll where demand appears. It shrinks no faster than the dwell column allows (asymmetry from PerfIso and Heracles [S]; dwell lengths after BOINC's 15 to 20 s [S]).

| Resource | Away | Present | Active | Game/Media | Shrink dwell | Enforced by |
|---|---|---|---|---|---|---|
| CPU (logical idle CPUs kept free of jobs) | 2 | 4 | max(6, peak non-job busy CPUs over 30 s + 2) | 8 | 1 CPU per 15 s | Job CPU set/affinity resize (PerfIso showed caps fail [S]); idle priority kept |
| RAM (available floor) | 5% (the 95% ceiling you chose) | 8% | max(5%, user working-set growth over 10 min + 2 GB) | Active + 2 GB | 60 s | Admission plus per-job commit cap (the earlier Windows-mechanics notes #2); kill ladder below |
| VRAM (kept free for non-job use) | 1.0 GB | 1.5 GB | max(1.5 GB, non-job dedicated peak over 10 min + 1 GB) | Game's observed peak + 1.5 GB | 120 s | Admission by learned job peaks; cooperative release |
| GPU compute | none | none | none beyond IDLE priority | No new grants; running jobs get a cooperative pause after 5 s | 30 s with no game | D3DKMT IDLE (already set) plus the pause protocol |

PerfIso's 8 of 48 logical cores is about 17% [S]. The "Active" CPU row lands near 6 of 16 logical CPUs (37%) because desktop bursts (compiles, browser, IDE) are less predictable than a search server's. Raise or lower it after measuring frame time with PresentMon [I].

### Market rules (band 2)

The order key is **decayed attained service per weight**. For each project, `S_p` is GPU-minutes charged, with a 12-hour half-life (Slurm-style decay, as the earlier Windows-mechanics notes §4 proposed). The waiting project with the lowest `S_p / w_p` goes next, where `w_p` comes from budgets.json. This is stride scheduling and 2D-LAS in one formula (sources above) [I]. The charge is DRF-style: `max(GPU-engine minutes, VRAM-GB-minutes / 16, RAM-GB-minutes / 32) × price(bid)`, so holding 12 GB of VRAM while idle still costs [I]. Bids become **paid urgency**. `price(b) = b / 5`: bid 5 is list price, 10 costs twice, 1 costs a fifth. Urgency shifts the order key by a bounded amount, at most a lead of 30 GPU-minutes of attained service, so it can jump the queue but never starve anyone (Tycoon pay-per-use [S]; numbers [I]). Budgets are **Karma-style buckets**: the daily allowance refills at a steady rate, the bank caps at 2 days, and an empty bucket drops the project to band 3 instead of bidding 0 [I]. Any ticket waiting **45 minutes** goes next regardless of key (a hard bound replacing linear aging) [I]. Every turn is a **lease**. `--minutes` sets the kill-check limit. The predicted runtime used for SRPT tie-breaks is the median of the last 5 actual/declared ratios for the (project, command hash) times the new `--minutes` (Tsafrir et al. [S]). At 1.25 × the lease, a job must call `firefighter extend` (as AgentLoom's `gpu_extend` [S]) or it drops to band 3 and its overrun minutes are charged at 2x [I].

### Anti-gaming rules

The rules carry this stance [I]. **Sybil:** tickets, budgets and attained service attach to the project (repo root, already `project_of`), never to sessions or jobs, so ten jobs get no more share than one (the lottery currency principle [S]). **Under-declared runtime:** ordering uses the corrected prediction, so a short claim gains nothing, and a project whose median ratio exceeds 1.5 pays a 25% surcharge. **Under-declared VRAM or RAM:** admission uses max(declared, learned peak × 1.2), and a job that exceeds its declaration at runtime pays the overrun at 2x and loses the next turn. **Hoarding:** an ESX-style idle tax [S] charges VRAM held while the job's GPU-engine time is under 15% at 3x (k = 1/(1−τ) with τ = 2/3). After 10 minutes of that, the turn is lost, which is the earlier Windows-mechanics notes's lease rule. **Information:** STATUS.md shows queue order, each job's ETA and its own price, but no rival bid values (InfoBid [S]). **Bid inflation through instructions:** CLAUDE.md states the price schedule in one sentence. Only the human can grant free urgency, through `firefighter boost <project>`.

### Preemption ladder

Each step is tried in order, and the next step fires only if the trigger persists past the dwell. User-triggered steps skip the min-runtime guard; band-vs-band preemption respects a 10-minute minimum guaranteed runtime (KAI [S]).

| Step | Action | Frees | Trigger | Cost | Source |
|---|---|---|---|---|---|
| 0 | Idle CPU priority, idle GPU priority, low memory and I/O priority | Nothing; reorders | Always | None | Current code; the earlier Windows-mechanics notes #5 |
| 1 | Shrink the job's CPU set to (16 − B) | CPU | Idle CPUs < B, within one poll | Throughput only | PerfIso [S] |
| 2 | Cooperative pause: set `FIREFIGHTER_PAUSE` (a named event or flag file) that the training loop checks every step; optionally `torch.cuda.empty_cache()` | GPU slices; cached VRAM | Game/Media state, or foreign 3D use > 20% for 5 s | About one step | Gandiva step-boundary suspend [S]; protocol [I] |
| 3 | NtSuspendProcess of the job tree, at most 60 s | GPU slices and CPU only; **not** RAM or VRAM | Step 2 ignored for 10 s | Risky if held long (paging) | the earlier Windows-mechanics notes §0 finding 1 |
| 4 | Graceful checkpoint-and-exit: CTRL_BREAK, or the `FIREFIGHTER_CHECKPOINT` flag, with 60 s grace, then requeue with priority kept | VRAM, RAM | VRAM or RAM below the reserve for 20 s; band-3 job when band 2 waits | Work since the last checkpoint (CheckFreq keeps overhead ≤ 3.5% [S]) | Borg eviction notice [S]; CheckFreq ([USENIX](https://usenix.org/conference/fast21/presentation/mohan)) |
| 5 | TerminateJobObject: band 3 first, then band 2; heaviest first within a band | Everything | Available RAM < 3%, or a paging-stall proxy above threshold for 10 s | Lost work | lmkd ordering, earlyoom two-stage [S] |

Jobs declare `--evict never|graceful|force` (gpubroker [S]). `never` jobs are admitted only while the user is Away and only in band 2, so the ladder never has to kill them for a band-2 rival. The user's own needs can still reach step 5 [I].

## Conclusion

Three findings change how FIREFIGHTER should be framed. First, the user's reserve is a *control loop*, not a setting. PerfIso's result that rate caps fail while a resized idle-core buffer works on Windows Job Objects is the strongest single piece of evidence here, and it argues against both the static 2-core reserve and the earlier idea of leaning on CPU-rate caps. Second, FIREFIGHTER's market problem is economic, not algorithmic. Any scheme where urgency is free collapses to everyone claiming maximum urgency, and studies of LLM bidders suggest agents will find that equilibrium faster than humans did on Mirage. Least attained service with priced urgency and leases removes the incentive without needing agents to be honest. Third, the hard limit on this machine is VRAM and the preemption it allows. Windows offers no transparent CUDA checkpoint and no VRAM fence, so the cooperation of the jobs themselves (pause flags, checkpoint-on-signal, declared eviction policy) is the real preemption mechanism. Making that protocol easy for agents to adopt matters more than any scheduling formula.

What remains unknown should be measured locally, not looked up. Nobody has published how D3DKMT IDLE priority interacts with hardware-accelerated GPU scheduling on RTX 50-series cards, how quickly NtSuspendProcess releases GPU slices under WDDM, or how biased coding agents' `--minutes` estimates are. FIREFIGHTER's log already holds the data for the last of these. A week of logging the actual/declared ratio, foreign-GPU events and per-job VRAM peaks before changing the constants would turn most of the [I] labels above into [local] ones.
